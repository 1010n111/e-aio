# 企业级一体化管理系统可行性研究报告

> **项目名称**：企业级一体化管理系统（e-aio）
> **项目定位**：通用能力大一统 + 业务逻辑按企业定制的企业级开源系统
> **编制依据**：GB/T 8567-2006《计算机软件文档编制规范》可行性研究报告章节
> **版本**：v3.0（全开源、非SaaS、Modulith单体、Vibe Coding）
> **日期**：2026-09-15

---

## 核心结论（执行摘要）

本项目为构建一个**通用能力大一统 + 业务逻辑按企业定制**的企业级一体化管理系统。经七维可行性论证，结论为**有条件可行，建议立项、分阶段推进**。

| 维度 | 结论 | 关键依据 |
|------|------|----------|
| 需求可行性 | 可行 | 现有 ERP/OA/CRM 孤岛割裂痛点真实存在，一体化需求明确 |
| 技术可行性 | 可行 | Spring Modulith 模块化单体 + Vibe Coding 技术栈成熟可控 |
| 组织可行性 | 可行 | 模块化单体降低团队协作门槛，适合开源社区共建 |
| 经济可行性 | 可行 | 全开源无商业化收费，成本为纯投入型，需持续志愿者与资助支持 |
| 法律可行性 | 可行 | 开源许可证、合规基线、多租户数据隔离均可满足 |
| 进度可行性 | 可行 | 36 个月三阶段，MVP 前置（9 个月） |
| 风险可行性 | 整体可控 | 社区活跃度与长期维护是核心风险 |

**四大核心约束（贯穿全文）**：
1. **不考虑 SaaS 模式**——本项目只做自托管部署（Self-hosted），不提供多租户云托管商业服务。
2. **系统全部开源，接受他人 PR**——以开放协作、社区共建为核心理念，接受外部贡献者提交 Pull Request。
3. **纯 Vibe Coding 开发**——采用 AI 辅助的 Vibe Coding 开发范式，人机协作快速迭代。
4. **Spring Modulith 模块化单体**——不做微服务，用模块化单体兼顾架构清晰与运维简单。

**推进路径**：垂直行业切入做深定制 → 9 个月交付 MVP → 补齐业务闭环 → 开放 AI 与模块扩展、发展社区生态。18 个月设评审点，若社区活跃度不足则调整投入策略。

## 1. 引言

### 1.1 编写目的

本报告论证「企业级一体化管理系统」项目在需求、技术、组织、经济、法律、进度与风险七个维度上的可行性，为立项决策提供依据。读者为项目发起人、核心贡献者、潜在资助方与早期采用企业。报告回答的核心问题是：**该系统能否做、是否值得做、以何种路径推进**。

### 1.2 项目背景

企业现有 ERP、OA、CRM 等系统长期存在系统孤岛、数据割裂、重复录入、定制成本高、报表能力弱等痛点：业务部门在多个系统间切换，数据口径不一致，管理层难以获得全局视图。同时，企业对**自主可控、开源透明、数据自持**的需求日益增长，不愿被商业 SaaS 绑定。本项目以"通用底座 + 行业定制 + 全开源 + 自托管"回应这一需求，让企业拥有数据的完全自主权。

### 1.3 项目目标与产品定位

**产品定位**：**通用能力平台 + 定制业务逻辑 + 全开源自托管**。平台内置 OA、CRM、库存、财务、工作流、审计、权限、审批、AI 等通用能力作为"大一统底座"；企业个性化业务逻辑（行业业务对象、专属流程、定制表单报表）通过主数据与配置化能力按需搭建。

| 维度 | 定义 | 目标客户 | 成功标准 |
|------|------|----------|----------|
| 通用层 | 通用能力开箱即用 | 所有企业 | 90% 通用需求零定制 |
| 定制层 | 行业业务对象 / 流程 / 表单 / 报表 | 垂直行业企业 | 单客户定制交付 ≤ 60 人天 |
| 底座层 | 主数据 + AI 平台 + 数据底座 | 平台自用 + 社区伙伴 | 支撑 80% 定制需求配置化实现 |

### 1.4 术语与参考资料

**术语**：模块化单体（Modular Monolith）、Vibe Coding、RBAC/ABAC、多租户、RAG（检索增强生成）、Agent 编排、主数据管理、自托管（Self-hosted）、PR（Pull Request）、审计（Audit）。

**参考资料**：GB/T 8567-2006《计算机软件文档编制规范》、GB/T 11457-2006《软件工程术语》、Spring Modulith 官方文档，以及文末所引市场研究报告。

## 2. 需求分析与现状

### 2.1 现有系统痛点（需求来源）

需求第一来源是现有 ERP/OA/CRM 的普遍痛点：

- **系统孤岛**：销售在 CRM 建客户不能同步到 ERP，OA 审批完凭证不能自动进财务，跨系统靠人工导出导入。
- **业务与系统脱节**：审批只走签字不校验业务数据，库存、合同、回款数据各说各话。
- **定制贵、改不动**：标准版不适配、定制开发周期长、升级即失效。
- **报表与 AI 能力弱**：跨系统经营分析做不出来，智能化应用停留在试点。
- **数据自主权缺失**：商业 SaaS 锁死数据、导出困难、订阅费用持续支出，企业数据安全与合规风险高。

本项目价值主张正是针对这些痛点：统一主数据、统一流程、统一权限、统一报表、内置 AI，**并让企业完全拥有自己的数据和代码**。

### 2.2 功能范围：通用能力全面补齐

项目功能范围分为三层：**通用能力层**（平台标准交付，全部补齐）、**定制业务逻辑层**（按行业/企业配置）、**AI 增强层**（嵌入各模块的智能化能力）。

> **主数据架构原则（单体模块化）**：本项目采用 Spring Modulith **模块化单体**架构，各业务模块与主数据模块同进程、同数据库。因此主数据**不做"分发复制"到各业务模块**，而是通过公共 API **实时共享访问（事务内强一致）**；主数据变更通过 **Spring 应用事件**驱动缓存刷新、审计、通知、搜索/数仓同步等副作用；**仅对跨系统边界（外部异构系统）才做真正的数据分发同步**。

#### 2.2.2 审计体系：系统操作审计 + 财务审计

审计是本项目的核心差异化能力之一，覆盖两大维度，保证"全过程可追溯、全数据可审计"。

**（一）系统操作审计（Security / Operation Audit）**

| 审计点 | 内容 | 实现方式 |
|--------|------|----------|
| 操作留痕 | 谁、何时、对哪个对象、做了什么操作 | 统一审计日志（用户ID、IP、时间、操作类型、对象、前后值） |
| 权限变更审计 | 角色授予/撤销、数据权限调整、审批人变更 | 权限变更事件记录 + 操作人追踪 |
| 数据快照 | 关键业务数据的变更前后快照 | 变更数据版本化，可回溯 |
| 登录审计 | 登录成功/失败、异常登录、异地登录 | 登录事件流 + 风控告警 |
| 导出/下载审计 | 敏感数据导出、批量下载 | 导出行为记录 + 水印 |
| 合规审计日志 | 满足等保、内控要求的审计日志 | 日志留存策略 + 防篡改 |

**（二）财务审计（Financial Audit）**

| 审计点 | 内容 | 实现方式 |
|--------|------|----------|
| 凭证审计 | 凭证生成、修改、审批全过程 | 凭证版本链 + 修改留痕 |
| 账实相符 | 账面与实物（库存、现金）核对 | 定期对账机制 + 差异追踪 |
| 四流合一 | 合同流、物流、资金流、发票流核对 | 四流数据关联校验 |
| 费用合规 | 报销、费用是否符合预算与制度 | 费用审计规则 + 审批留痕 |
| 财务变更审计 | 会计科目调整、冲销、反结账 | 财务操作审计日志 + 审批链 |
| 报表审计 | 财务报表数据来源可追溯 | 报表钻取到底层凭证 |

#### 2.2.3 权限体系：母子公司架构

本项目权限体系**以母子公司（集团-下属公司）多级组织架构为核心设计**，兼顾组织层级、数据隔离与授权管控。

**（一）多级组织架构**

```
集团总部（母公司）
├── 事业部 / 区域
│   ├── 全资子公司A
│   │   ├── 部门/团队
│   │   └── 岗位/角色
│   ├── 控股子公司B
│   └── 参股公司（权限受限）
└── 共享服务中心（财务/人力/IT）
```

- **组织树**：支持集团 → 子公司 → 部门 → 岗位 → 用户的完整层级树。
- **多组织节点**：同一用户可挂载到多个组织节点（如兼任总部与子公司职务）。
- **组织生命周期**：子公司成立、合并、注销时的权限自动迁移与清理。

**（二）数据权限隔离**

| 维度 | 规则 |
|------|------|
| 组织隔离 | 子公司数据默认仅本公司可见，集团可配置全局/汇总视图 |
| 数据行级权限 | 按组织、部门、责任人、数据归属过滤 |
| 共享机制 | 跨公司数据共享需显式授权（如集团财务看子公司账） |
| 字段级权限 | 敏感字段（薪酬、成本）按角色隐藏/脱敏 |

**（三）角色与授权模型**

- **RBAC 角色权限**：角色 → 权限点，角色可全局或限定组织范围。
- **ABAC 属性权限**：按组织属性、数据属性、时间、上下文动态判定。
- **角色继承与覆盖**：子公司角色可继承集团模板，集团可统一管控或下放。
- **职责分离（SoD）**：不相容岗位（如记账 vs 审批）自动冲突检测。

**（四）母子公司专项场景**

- **集团统一管控**：集团可统一下发权限模板、审计策略、财务规则到子公司。
- **子公司自治**：子公司可独立配置内部角色、流程、数据权限，集团不干预。
- **跨公司审批与审计**：集团与子公司间跨级审批、上级审计下级，全程留痕。
- **合规隔离**：涉密子公司数据与集团共享服务严格隔离。

### 2.3 非功能需求

| 类别 | 要求 | 指标（初期） |
|------|------|--------------|
| 性能 | 多组织并发、流程审批实时 | 单实例 2,000 并发用户；流程节点响应 < 2s |
| 可用性 | 自托管部署，单机/集群均可 | 单体部署即可满足；支持横向扩展 |
| 安全 | 数据隔离、权限最小化、审计留痕 | 等保三级目标；操作日志全量可追溯 |
| 可维护性 | 模块化、易升级、易扩展 | Spring Modulith 模块边界清晰，模块可独立演进 |
| 开源可协作性 | 代码规范、文档齐全、可接受外部 PR | 模块化结构 + 自动化测试 + CI 门槛 |

## 3. 技术可行性

### 3.1 总体结论

技术可行性结论：**可行，且无不可逾越的技术障碍**。本项目明确**不采用微服务架构**，而是采用 **Spring Modulith 模块化单体（Modular Monolith）**，配合**纯 Vibe Coding 开发范式**。该组合兼顾架构清晰度、部署运维简单度与社区协作便捷度，是开源企业级系统的理想选择。

### 3.2 架构选型：Spring Modulith 模块化单体

#### 3.2.1 为什么不用微服务

| 维度 | 微服务 | 模块化单体（Spring Modulith） |
|------|--------|-------------------------------|
| 部署运维 | 复杂，需容器编排、服务发现、分布式追踪 | 简单，单一可执行产物，单机即可运行 |
| 一致性 | 分布式事务复杂 | 单体事务天然强一致（金融/库存强需求） |
| 团队协作 | 服务边界割裂，跨服务沟通成本高 | 模块边界清晰，但仍在一个代码库/进程 |
| 资源占用 | 高（每个服务独立进程） | 低，适合中小企业与自托管 |
| 演进难度 | 高 | 低，模块可逐步演化为独立服务 |

**结论**：本项目以中小企业、集团化企业自托管为目标，事务一致性与部署简单优先，模块化单体是最优解。

#### 3.2.2 Spring Modulith 核心设计

- **模块边界**：以业务域划分模块（如 `oa`、`crm`、`inventory`、`finance`、`workflow`、`audit`、`security`、`approval`、`ai`、`hr`、`project`、`scm`、`report`、`portal`、`mdm`、`marketing`、`service`、`fund`、`integration`、`mobile`、`i18n`），模块间通过明确的公共 API 交互。
- **通用能力与业务模块分层**：系统分为**通用能力层**（OA、CRM、库存、财务、工作流、审批、权限、审计、AI、报表等，平台统一提供、各企业一致）与**业务模块层**（按行业/企业定制的具体业务逻辑，独立成模块）。**业务模块单向调用通用能力**（复用流程、权限、审计、报表、AI 等公共服务），依赖方向为"业务模块 → 通用能力"，禁止反向依赖；通用能力保持稳定，业务模块可插拔、可定制、可独立演进。
- **模块依赖**：依赖方向单向、清晰，禁止循环依赖；使用 ArchUnit 强制校验。
- **事件驱动**：模块间通过 Spring 应用事件（Application Events）异步解耦（如"合同创建"→触发"应收生成"）。
- **独立数据归属**：每个模块拥有自己的数据库 Schema / 表空间，跨模块通过应用层接口访问，禁止直接操作他人表。
- **模块独立演进**：模块可独立打包、独立测试、独立扩展，未来必要时可平滑拆分。

#### 3.2.3 技术栈（开源优先）

> **版本与开源优先原则**：核心框架采用 **Spring Boot 4.1.x（最新稳定版，基于 Spring Framework 7）** 与配套的 **Spring Modulith 2.1.x** 模块化单体；全技术栈**优先选用成熟开源项目**，仅极少数行业定制模块为自研并开源。全栈开源可控、无商业闭源依赖，保障企业可自托管、可审计、可二次开发。

| 层 | 技术选型（开源优先） |
|----|----------|
| 代码蓝本 | RuoYi-Vue（前后端分离版，Apache-2.0）→ 以 Spring Boot 4.x + Spring Modulith 2.x 重构为模块化单体 |
| 语言/框架 | Java 21（或更新 LTS）+ **Spring Boot 4.1.x + Spring Modulith 2.1.x**（开源） |
| 工具库 | Lombok / Hutool / Bean Validation / MapStruct（均开源） |
| 前端 | Vue 3 + Vite + Element Plus（RuoYi-Vue3 蓝本，开源）+ 配置化渲染引擎 |
| 数据库 | PostgreSQL（开源，主库，事务强一致）+ Redis（开源，缓存/会话） |
| 缓存 | Redis（开源，分布式缓存）+ Caffeine（开源，本地缓存，二级缓存） |
| 定时任务 | Quartz / XXL-JOB（开源）或 Spring Task + ShedLock（分布式锁防重） |

### 3.3 开发范式：纯 Vibe Coding

**Vibe Coding 定义**：以 AI 辅助编码为核心的开发范式，开发者通过自然语言描述需求、AI 生成代码、人机协作迭代，重点从"手写每一行"转向"设计意图、审查产出、保障质量"。

#### 3.3.1 Vibe Coding 落地方式

- **AI 驱动开发**：使用 Cursor / GitHub Copilot / Claude Code 等工具，通过自然语言指令生成模块代码、测试、文档。
- **人机协作流程**：人负责架构与需求边界，AI 负责实现与初稿；人负责评审与合并。
- **测试驱动**：AI 生成测试，人补充边界用例；关键模块要求测试覆盖率门槛。
- **代码评审**：每个模块合并需通过 Code Review，外部 PR 同样执行评审门槛。
- **文档同步**：AI 同步生成 API 文档、模块说明、变更记录。

#### 3.3.2 Vibe Coding 的可行性评估

| 维度 | 评估 | 风险与对策 |
|------|------|-----------|
| 效率 | AI 生成基础 CRUD、表单、报表效率高 | 合理拆解模块，AI 聚焦生成"脚手架+模板" |
| 质量 | AI 代码质量依赖 Prompt 与评审 | 强制 Code Review + 自动化测试 + ArchUnit 约束 |
| 一致性 | 多模块风格易漂移 | 统一代码规范、模板、Lint 规则约束 |
| 架构约束 | AI 可能绕过模块边界 | ArchUnit 静态校验 + 依赖规则自动化 |
| 可维护性 | 需保证可读可维护 | 模块文档 + 清晰的模块 API |

**结论**：Vibe Coding 在本项目（模块化单体、边界清晰、有强测试与约束）中可行且高效，但必须配套**严格的自动化质量门**（ArchUnit、测试覆盖、Lint、CI）防止架构腐化。
