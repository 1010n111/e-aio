## 1. 引言

### 1.1 编写目的

本文档作为 **e-aio 企业级一体化管理系统** 的软件需求规格说明书，明确系统的功能需求、非功能需求、外部接口需求与约束条件，作为**需求基线**，供设计、开发、测试、验收与部署各阶段共同遵循。

本文档读者对象：项目管理者、架构师、开发工程师、测试工程师、实施与运维人员、评审与验收人员、潜在开源贡献者。

### 1.2 项目背景

企业现有 ERP、OA、CRM 等系统长期存在系统孤岛、数据割裂、重复录入、定制成本高、报表能力弱、审计缺失等痛点，且商业 SaaS 存在数据锁死、订阅费用持续、合规风险高等问题。本项目旨在构建**全开源、纯私有化自托管、通用能力大一统、业务按企业定制、适配集团母子公司架构、具备系统 + 财务双审计体系**的一体化管理系统，让企业拥有数据完全自主权。

### 1.3 项目目标

1. **一体化**：将 OA、CRM、库存、财务、HRM、项目、供应链、工作流、审批、权限、审计、报表、AI、门户等通用能力集成为一个统一平台。

2. **可定制**：通过主数据与配置化能力，业务逻辑按企业需求定制，无需深层二次开发。

3. **全开源**：全部代码开源、接受社区 PR，无 SaaS、无商业收费，企业可自托管。

4. **集团化**：原生支持母子公司多级组织、数据隔离、跨公司审批与审计。

5. **合规审计**：系统操作审计 + 财务专项审计双体系，满足企业内控与合规要求。

6. **模块化**：采用 Spring Modulith 模块化单体，低运维、高内聚、可演进。

## 2. 总体描述

### 2.1 产品视角

e-aio 是一套**单实例、多组织、模块化的企业级一体化系统**。系统以通用能力底座为基础，通过主数据与配置化能力承载企业定制业务，以母子公司权限体系实现集团化管控，以双审计体系保障合规。系统采用 Spring Modulith 模块化单体架构，自托管部署，全开源。

**架构分层原则**：系统分为**通用能力层**（OA、CRM、库存、财务、工作流、审批、权限、审计、AI、报表等，平台统一提供、各企业一致）与**业务模块层**（按行业/企业定制的具体业务逻辑，独立成模块）。**业务模块单向调用通用能力**（复用流程、权限、审计、报表、AI 等公共服务），依赖方向为"业务模块 → 通用能力"，禁止反向依赖；通用能力保持稳定，业务模块可插拔、可定制、可独立演进。

```
┌──────────────────────────────────────────────────────┐

│                  统一工作台门户（Web）                │

├──────────────────────────────────────────────────────┤

│   OA │ CRM │ 库存 │ 财务 │ HRM │ 项目 │ 供应链        │

├──────────────────────────────────────────────────────┤

│   工作流 │ 审批 │ 权限 │ 审计 │ 报表BI │ AI │ 消息     │

├──────────────────────────────────────────────────────┤

│               配置化业务定制（主数据 / 规则）          │

├──────────────────────────────────────────────────────┤

│      Spring Modulith 模块化单体（Spring Boot 4.x）    │

├──────────────────────────────────────────────────────┤

│   PostgreSQL │ Redis │ OpenSearch │ ClickHouse │ 向量库│

└──────────────────────────────────────────────────────┘
```

### 2.4 运行环境与约束

| 约束项  | 要求                                                       |
| ---- | -------------------------------------------------------- |
| 部署模式 | 自托管（Self-hosted），企业私有化部署，**无 SaaS 多租户托管**                |
| 运行平台 | 支持 Linux/Windows 服务器；适配信创环境（麒麟 / 统信 OS、国产数据库、国产中间件）      |
| 技术栈  | Java 21 + Spring Boot 4.1.x + Spring Modulith 2.1.x；开源优先 |
| 数据库  | PostgreSQL（主库）+ Redis（缓存）                                |
| 开源协议 | Apache-2.0 拟采用；全代码开源、接受 PR                               |
| 浏览器  | 支持主流现代浏览器（Chrome/Edge/Firefox/Safari 最新两个大版本）            |

### 2.5 假设与依赖

1. 企业具备自托管的基础 IT 环境（服务器、数据库、网络）。

2. 集团化企业存在明确的组织层级（母子公司）与数据隔离诉求。

3. 系统依赖开源组件（PostgreSQL、Redis、Flowable 等）的可用性与维护。

4. 财务审计规则需财务领域专家参与建模，不同企业核算规则存在差异。

5. AI 能力依赖大模型服务，允许企业接入自有或第三方模型。

#### 3.15.3 主数据共享访问与集成（FR-MDM-DIS）

> **架构原则**
>
> ：本项目采用 Spring Modulith 
>
> **模块化单体**
>
> 架构，各业务模块与主数据模块运行于同一进程、同一数据库。因此主数据
>
> **不做 "分发复制" 到各业务模块**
>
> ，而是通过主数据模块的
>
> **公共 API 直接访问（实时读取、事务内强一致）**
>
> ；主数据变更通过 
>
> **Spring 应用事件**
>
> 触发下游副作用（缓存刷新、审计、通知、搜索 / 数仓同步），
>
> **仅对跨系统边界（外部异构系统）才做真正的数据分发同步**
>
> 。

| 编号            | 需求      | 优先级 | 说明                                                                        |
| ------------- | ------- | --- | ------------------------------------------------------------------------- |
| FR-MDM-DIS-01 | 模块内共享访问 | P1  | 主数据通过公共 API 供各业务模块（CRM / 库存 / 财务 / 采购等）实时读取，事务内强一致，不做数据复制分发               |
| FR-MDM-DIS-02 | 变更事件    | P1  | 主数据创建 / 变更 / 停用发布 Spring 应用事件，驱动缓存刷新、审计留痕、通知、搜索 / 数仓同步等副作用（Modulith 事件解耦） |
| FR-MDM-DIS-03 | 对外集成接口  | P1  | 提供 OpenAPI，供外部异构系统（第三方 ERP / 数据平台）消费主数据；跨系统边界时才做数据同步                      |
| FR-MDM-DIS-04 | 同步监控    | P2  | 对外 / 跨系统同步任务状态、失败重试、一致性校验                                                 |

## 6. 数据需求

### 6.1 数据分类

| 数据类别     | 说明          | 安全级别        |
| -------- | ----------- | ----------- |
| 组织与用户    | 组织、用户、角色、权限 | 高           |
| 财务数据     | 凭证、账务、报表、预算 | 极高（加密 + 审计） |
| 客户 / 商机  | 客户、联系人、合同   | 高           |
| 库存 / 供应链 | 商品、出入库、采购   | 中高          |
| 人力资源     | 员工、薪酬       | 极高（敏感）      |
| 审计日志     | 操作审计、财务审计   | 极高（防篡改）     |
| 业务数据     | 各业务模块数据     | 按公司 / 数据权限  |

### 6.2 数据隔离

* 集团数据按 "组织维度" 隔离（FR-PERM-ORG）。

* 审计日志全局归集，母公司可查全集团（FR-AUD-SYS-05）。

* 财务数据强一致、可追溯（FR-FIN/FR-AUD-FIN）。

### 6.3 数据生命周期

* 备份、归档、导出、清理策略；

* 审计日志长期保存、防篡改、可校验。

## 7. 约束与假设（补充）

### 7.1 设计约束

1. **不采用微服务**：采用 Spring Modulith 模块化单体，单一可执行产物。

2. **不采用 SaaS**：纯自托管、私有化部署，无多租户云托管逻辑。

3. **开源优先**：技术选型优先开源组件，仅行业定制模块自研并开源。

4. **Vibe Coding**：以 AI 辅助编码为核心开发范式，配套自动化质量门。

5. **架构质量门**：ArchUnit 校验模块依赖、测试覆盖门槛、Lint、CI。

### 7.2 假设

1. 企业具备自托管基础设施与运维能力。

2. 集团化企业存在明确组织层级与数据隔离诉求。

3. 财务核算规则需领域专家建模，存在行业 / 企业差异。

4. AI 依赖大模型服务，企业可自主选择接入。
