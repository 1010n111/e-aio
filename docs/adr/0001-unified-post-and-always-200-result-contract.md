# ADR-0001：统一 POST + JSON 与「HTTP 状态码恒 200」的契约

- 状态：已接受
- 日期：2026-09-19
- 适用批次：P0 冻结，全批次有效
- 相关：`docs/agents/api-conventions.md`、04-DD P0 册 3.2 / 3.3、HLD 2.6.4 / 7.1 / 7.2

## 背景

全部接口需前后端一致、可由单一封装处理，且对外集成（P3 integration）也复用同一契约。HTTP 状态码语义与"业务结果"存在两套并行表达方式，必须二选一：用 HTTP 状态码表达失败语义，还是把业务结果全部收进响应体。

## 决策

1. 全部接口使用 **POST + JSON body**（含查询、删除、导出）；文件上传走 `multipart/form-data`、下载走二进制流，为唯一例外。
2. **HTTP 状态码恒为 200**；业务结果由 body 的 `code` 表达。认证/鉴权失败同样返回 200 + `10401`/`10403`；不可读报文、缺参、方法不支持等传输层错误也归一为 200 + `10000`/`10001`。
3. 响应体统一为 `Result<T>`（`code` / `message` / `data` / `traceId`），分页为 `Result<PageResult<T>>`；异常统一由全局异常处理器转换，**不向客户端泄漏堆栈**。

## 被否决的备选

- **按 HTTP 状态码表达业务错误**（4xx/5xx 承载业务语义）：业务错误码空间会被挤进几十个状态码，新错误类型必须复用相近状态码，前端与网关都需要额外映射表；且与 RuoYi 蓝本改造（统一 POST）后的单一封装目标冲突。
- **恒 200 但把错误放在 header/信封双层结构**：错误信息出现两个来源，监控与前端都要解析两处，收益仅是"更像 HTTP"。

## 后果（含代价）

- 中间件、网关、APM、浏览器**无法按状态码识别业务失败**：告警面改为 `/actuator/health` + ERROR 日志 + traceId，而非 HTTP 5xx 比率。
- 认证失败恒 200 会使标准 OIDC/SSO 对接与部分安全扫描器"看起来正常"。
- **前端禁止按 HTTP 401/403 判断跳登录**，必须按 `Result.code`（`10401`/`10403`）判断。
- 长任务（导出/批量导入）不得依赖"长连接返回结果"，需以任务 ID + 轮询查询结果（P1 Scheduler）。
